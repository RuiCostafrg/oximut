# M2: mutation switching and persistent controllers

M2 adds an opt-in execution mode while retaining the M1 fresh-process reference:

```sh
cargo build -p oximut-cli --locked
target/debug/oximut --root fixtures/m2 --source src/subject.ts \
  --execution persistent --order-seed 17 --report .oximut/m2.json
```

Use the pinned Linux Node executable on `PATH` (see the lifecycle ADR for
Android/PRoot). `--execution fresh` remains the default. The seed changes only
execution order; mutant identities and report semantics stay stable.

## Switching and isolation

Compatible mutants in one file share a transformed module and source map.
Inline conditional expressions select the active mutation without wrapping
expressions in functions, preserving operand order, side effects, `await`, and
`yield`. The adapter sets `OXIMUT_ACTIVE_MUTANT` before test module evaluation and
clears it after each run. This is a reserved runner environment key; projects
must not change it. Files that refer to or bind `process` conservatively use
individual static transforms, avoiding a shadowed selector. Oversized or
grammar-incompatible shared transforms also fall back explicitly.

The CLI runs the original baseline, then one instrumented baseline that serves
every shared transform at once with no active mutant. It must pass with test
counts identical to the original baseline; any failure blocks mutation
execution. Mutant jobs keep serving exactly these validated shared transforms
(the `resident` request field); only the selector changes, and a static mutant
overrides its own file. With `--test-selection`, the shared transforms also carry
coverage probes, so the same run collects coverage from the code mutants execute.
Absent probe collectors make the probes no-ops. Like `OXIMUT_ACTIVE_MUTANT`,
`globalThis.__oximut_m3_hit__` is reserved; projects must not define it. Shared
instrumentation is visible to `Function.prototype.toString()`, as switched code
always was. The coverage run reports source reflection as incomplete coverage,
so the affected mutants run their full suites.

Executed results must acknowledge how many resident modules the adapter served.
Adapters that ignore `resident` therefore fail closed instead of reporting
unvalidated results. A request is limited to 8 MiB, so the CLI plans resident
groups. Normally a single group covers every file. Groups split only when the
modules plus a duplicate active module would exceed the budget. Each group is
validated by its own instrumented run, and its mutants serve only that group. A
lone module is served through `mutation` alone. If the coverage transforms
cannot fit in one request, coverage is marked incomplete
(`coverage-request-exceeds-limit`) and every mutant runs its full suite.
Source files are never rewritten.

The adapter and safe Vitest controller state persist. Every job still uses
isolated test workers with fresh evaluated module state.
`--isolation fresh-process` is the default: a fresh Vitest fork per test file.
`--isolation fresh-thread` opts into a fresh Vitest worker thread per test file,
using `pool: 'threads'` with `isolate: true`. It requires `--execution persistent`.
Parallel native runs share one controller by default for either isolation mode;
each mutant gets one fresh worker for all selected files. `--no-shared-controller`
uses a separate controller per worker and a fresh test worker per file.
Threads share the controller process. `process.chdir` is unsupported in threads.
Native addons and process-global state, including `process.env` mutations, follow
Vitest's threads semantics. A native-code crash takes down the controller and
is an infrastructure error. This mode does not provide process isolation.

Import-time mutations take effect on each run. Changing the transformed file or
code invalidates the module transform graph for exactly the files whose served
module changed; consecutive switched mutants in the same resident group
invalidate nothing, while moving to another group invalidates the files whose
served module changes. Entering or
leaving a coverage run still invalidates the whole graph so every probed file is
transformed and observed. Controller reuse does not imply
reuse of test workers, module singletons, or external application state.

Custom Vite plugins, global setup, and symlinked project inputs trigger a fresh
controller fallback. Multiple projects and resolved configurations that change
the requested pool, disable isolation, use a non-Node environment, or request
unsafe parallelism are rejected before test execution. JSON report diagnostics
record the observed reuse boundary. The controller is recycled after 50 jobs and when
project input metadata changes. Dependency installations and inputs outside the
project root must remain unchanged during a session; persistent mode is not a
watch mode or a concurrent-edit cache.

## Failure handling

Mutant jobs set Vitest's `bail` to 1; baseline jobs explicitly use 0, including
when a project config requests bail. Both the prior config and the cancellation
observer are restored in `finally`. Passing mutants and baselines run their full
selected inventory.

In pinned Vitest 5.1.0, `serializedConfig` calls `_serializeOverriddenConfig()`
for each worker start (`dist/chunks/index.Di8au7q4.js:5287,6572,6762`);
serialization reads current `config.bail` (`:4034`). The worker requests
`test-failure` cancellation (`dist/chunks/index.w_oBZ9N8.js:199`), forwarded to
`cancelCurrentRun` (`index.Di8au7q4.js:5109`). `onTestRunEnd` reports `interrupted`
when cancellation is active (`dist/chunks/cli-api.COfZo8lK.js:12284`). Because
`runFiles` clears cancellation listeners (`:13527`), the adapter observes the
public cancellation entry point for the duration of the job.

Only a mutant with an actual failed test carrying errors, an interrupted run,
and exclusively `test-failure` cancellations may accept unfinished tests.
Unhandled errors, process exits, module/suite errors and timeouts retain their
classification precedence; cancellation alone cannot kill a mutant. The adapter
reports `failed`, which the coordinator maps to a killed mutant.

Jobs run sequentially with individual deadlines that include controller
start-up. A timeout destroys the controller and its owned process tree. Worker
crashes are infrastructure errors, never mutation kills. Controllers are
periodically recycled. Surviving descendants force controller cleanup before
the next job, including detached descendants tracked by the Linux subreaper.

For the reference adapter, the Rust slot is the native execution coordinator.
It starts `m2-worker.ts` itself and exchanges one JSON message per line over a
dedicated Node IPC socket (never stdout/stderr). Neither the `m2-runner.mjs`
relay nor the Python supervisor is in this path. The slot keeps the relay's
contract:
- per-job deadlines;
- controller recycling on input metadata changes, plus content hashes for
  entries whose timestamps could hide a same-tick rewrite;
- at most 50 jobs per controller;
- retirement after timeouts and infrastructure errors;
- leak detection after each job from fresh broad process discovery.

Cleanup signals only pidfd-pinned identities whose start time still matches. It
succeeds only when every owned process has exited and been reaped. Without
pidfd support, persistent execution fails closed. The controller validates every
request; replies are bounded to the 1 MiB response limit, and Rust validates
response identity. Any other `--adapter` keeps the file-protocol relay: bounded
JSON files in a private session directory, published with atomic renames.
Either way, malformed or stale responses invalidate the controller or session,
and final cleanup failures make the report incomplete.

## Validation and measurement

The measurements recorded in this section were taken on Vitest 4 and do not
validate performance on the pinned Vitest 5.1.0 (see `docs/vitest-5-audit.md`).

```sh
python3 -m unittest discover -s tests -v
node --test packages/vitest-adapter/test/m2.test.mjs
python3 benchmarks/m2.py --repetitions 3 --warmups 1 --output .oximut/m2-benchmark
```

The acceptance corpus covers known kills and survivors, import-time switches,
nested arithmetic and operand side effects, async and generator expressions,
mocked imports, hooks, and module state. Two shuffled persistent orders must
agree by mutant identity with fresh execution, and fixture hashes must remain
unchanged. Adapter tests inspect worker/controller identities and recovery.

The benchmark alternates fresh and persistent mode order and saves every
report, elapsed-time sample, and tool/environment metadata. It refuses to
summarize incomplete runs or outcome disagreements. Timings include baselines,
disabled-switch validation, and final cleanup. They measure end-to-end elapsed
time only; they do not establish CPU or memory savings or a comparison with
Stryker. This is a small Linux-only corpus, not broad project compatibility.

[Recorded M2 results](../benchmarks/results/2026-10-24-m2-arm64/README.md)
contain one warmup and three measured pairs per fixture. Median fresh/persistent
ratios were 1.49× (M1), 2.53× (M2), and 1.39× (stateful). All 14 mutant outcomes
agreed across modes and orders. These measurements meet the M2 gate on this
corpus; they do not justify changing the default or widening compatibility.

External services, persistent files written by tests, native resource state,
and concurrent-test attribution remain outside the proven isolation boundary.
Opt-in test selection and no-coverage attribution are described in [M3](m3.md).

Baseline requests may carry `workers` (integer 1..1024, default 1). The persistent
controller sets `project.config.maxWorkers` for each baseline run; mutant runs
always set it to 1, even if the request carries a larger limit. `maxConcurrency`
remains 1, and pool/isolation validation remains unchanged. With the default
`forks` pool and `isolate: true`, every file gets a fresh process.

Pinned Vitest 5.1.0's `dist/chunks/index.Di8au7q4.js` groups specifications
inside every `executeTests` call (`:6096`), reads `project.config.maxWorkers`
(`:6289-6290`), then calls `pool.setMaxWorkers` for each group (`:6176`).
Isolated runners bypass reuse and stop after each task (`:5943-5951`). The
controller drains termination promises before acknowledging the job, then
restores configuration. See [the Vitest 5 audit](vitest-5-audit.md) for all
source anchors and the required filesystem-cache disablement.

Coverage setup writes one JSONL stream per PID/thread in a private job directory.
After workers terminate, the controller merges streams, checks the aggregate
record limit and ready count, and sorts test identities independently of file
completion order. Probe jobs invalidate transforms to obtain fresh observation
evidence even for repeated identical probe requests.
