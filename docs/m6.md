# M6 — Benchmark and alpha release decision

M6 adds a reproducible, correctness-gated benchmark workflow, a versioned report
schema, a compatibility boundary, and a tested source installation. Public alpha
publication remains **on hold**. The proposed 2× full-run speed and 30% memory
reduction targets require equivalent mutation scope and representative projects;
a fixture comparison with only partial Stryker overlap cannot satisfy those gates.

## Release scope

The working name is **Oximut**, and repository code uses the [MIT license](../LICENSE).
An npm registry lookup for `oximut` returned HTTP 404 on 2026-10-26. This is a
point-in-time observation, not a reservation, trademark clearance, or guarantee
that npm will accept publication. Recheck before publishing. No public npm or
crates.io package is created by this milestone; both manifests remain private.

Distribution for evaluation is a Linux source checkout with the pinned toolchain.
The [source installer](install.md) stages a release binary, matching adapters,
and the locked npm dependency graph. Its launcher resolves installed adapter
paths for fresh and persistent modes, including after relocation. The installation
smoke runs outside the checkout and observes actual adapter entrypoints.
The full dependency bundle is intentionally larger than a future runtime package.

See the [compatibility matrix](compatibility.md) and
[report reference and JSON Schema](report-schema.md). Memory control remains
sampled Linux process-tree admission and cancellation, not an installed hard cap.
The tested support boundary does not expand merely because packaging exists.

## Evidence and interpretation

The [benchmark protocol](benchmarks.md) defines the broader release experiment.
The [M6 harness commands](../benchmarks/README.md#m6-correctness-gated-measurements)
cover clean execution and incremental/forced pairs. Raw measurements retain
warmups, individual attempts, failed gates, exclusions, commands, configuration
hashes, and environment details. Phase metrics that tools do not expose remain
unavailable. OS caches are left untouched; builds and dependency installation
are outside timings.

Clean timing and incremental timing are separate claims. An unchanged cache run
still includes baseline validation. Input-change probes preserve test behavior;
they test cache policy, not a representative developer edit distribution.
Only Oximut changed-input gates establish conservative invalidation; Stryker
pairs record native reuse and outcome agreement, not equivalent invalidation
policy. Single-repeat correctness probes must not be presented as performance
estimates.

The [recorded M6 campaign](../benchmarks/results/2026-10-26-m6-arm64/README.md)
includes five measured clean repetitions after warmup. All clean correctness
gates passed. Within Oximut, persistent execution reduced median wall time versus
the fresh reference by 2.76× on pure functions and 1.71× on the stateful fixture,
with roughly 14% and 5% higher median peak RSS. The memory target therefore cannot
be inferred from controller reuse. Stryker exact overlap was 16 of Oximut's 18
pure mutants and all 4 stateful mutants, against Stryker scopes of 33 and 5;
unequal full scopes suppress cross-tool speed ratios.

The corrected unchanged-cache campaign also passed every correctness gate, but
Oximut's median warm time was **22.37 s versus 6.12 s forced** on the small M1
fixture, despite reusing all three outcomes. Baseline validation remains included.
Cache-enabled overhead outweighs the saved test work here; no incremental speed
claim is supported. The raw archive also retains an earlier rejected campaign
whose changing report destination/environment correctly invalidated the cache.
The harness now holds those inputs stable and regression-tests that condition.

All seven Oximut changed-input probes—source, tests, imported helper, snapshot,
config, lockfile, and declared environment—invalidated every outcome and agreed
with their forced run. These benign edits are single-repeat correctness probes,
not representative incremental performance measurements. The existing M1–M5
suite also passed all 33 checks, including explicit resource-failure behavior.
The installer was validated outside the checkout after relocation.

## Design and release follow-up

Keep fresh-process execution as the reference, controller-only persistent reuse,
whole-file conservative selection, and project-wide cache invalidation. The next
evaluation should match Stryker mutations exactly and measure controller residency
and startup costs before pursuing a memory-reduction claim. Profile the complete
cache-enabled path before claiming incremental gains, retaining all declared and
inherited input safeguards and baseline validation. The clean results
show why elapsed-time gains alone do not establish the memory target. Measure
these improvements separately. Do not weaken isolation or treat an unexplained
classification mismatch as a performance tradeoff.

Before a public alpha performance claim:

- Resolve every unexplained classification difference and pass correctness,
  cache-invalidation, and resource-failure gates on the release revision.
- Establish a truly equivalent mutation scope with Stryker; keep excluded and
  skipped work visible rather than crediting fewer mutants as faster execution.
- Add permission-cleared real projects at pinned revisions, generated scaling,
  and repeated measurements under multiple CPU/memory allocations on a native
  Linux host. Report regressions and revise the proposed targets from evidence.
- Recheck package availability, test the final public distribution artifact, and
  define supported binary targets and artifact provenance before publishing.

This is a decision to continue source evaluation with explicit release blockers.
It is not an announcement that the original performance targets have been met.
