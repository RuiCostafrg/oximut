#1 Fresh-fork bootstrap on the critical path: up to 334 ms (16% of the capture)

449 ms of every run waits for the slowest fork of each job to boot (max of spawn → started per job: 115, 86, 93, 101, 55 ms). Starting the next job's forks while the current one runs would hide all but the first job's.

Not covered by an open thread. A prewarmed spare fork (#45) was closed under the earlier CPU/RSS rule; wall time is now the only acceptance metric, so a pre-spawned idle fork pool deserves a fresh measurement.

#2 Instrumented baseline runs after the original baseline: up to 316 ms (16% of the capture)

The second baseline job takes 316 ms of controller-visible time (controller CPU 186 ms). Overlapping it with the original baseline is bounded by the controller CPU they share.

Tried at 4 and 2 workers on this workload and rejected: PR #59 ran it concurrently on a second slot and measured no wall gain (4 workers: after/before 0.991 [0.957, 1.249]; baseline phases 1292 → 1282 ms) at +15% CPU. The two baselines are CPU-bound, so overlap does not reach this bound; only a shorter instrumented run would.

#3 First mutant batch pays for cold lanes: up to 303 ms (15% of the capture)

The first full batch takes 537 ms against a median of 234 ms for the later full batches; its controller CPU is 490 ms of that wall.

Tried and rejected on this workload: PR #61 built the lane context on a spare controller during the baselines and was slower (after/before 1.082 at 4 workers), so moving that setup off the critical path did not help. It did not isolate createVitest from the other setup, so this report does not claim setup is free. This capture shows where the batch's time goes: cold per-lane module fetch and collect (184–290 ms against 19–64 ms in later batches) against 114 ms before its first fork.

#4 Controller boot before the first job: up to 220 ms (11% of the capture)

182 ms from Node start to the initialize request plus 37 ms to answer it (Node, Vitest import, createVitest).

Candidates: a persistent Node compile cache for the controller (V8 validates entries by content), or shipping the controller entry as plain JavaScript so Node skips type stripping.

#5 Idle lanes and gaps between mutant batches: up to 158 ms (8% of the capture)

After the first batch, lanes sit idle for 370 lane-ms (the last batch runs 2 of 4 lanes); consecutive batches are 66 ms apart in total.

Candidate: refill a lane as soon as its mutant finishes instead of waiting for the whole batch.

#6 Teardown after the controller closes: up to 59 ms (3% of the capture)

Rust-side teardown is 63 ms of which the controller close is 4 ms; the rest is verified descendant cleanup.

Verified descendant cleanup must stay; only its polling cadence is a candidate.

Why the controller matters

One controller process serves all 4 lanes. In the profiled run its main thread is busy 1750 ms, of which Vite transform/resolve is 36%, Node bootstrap and module loading 26%, GC 7%, and the synchronous part of spawning forks 96 ms. In the controller-job capture its CPU is 236 of 349 ms, 186 of 316 ms, 490 of 537 ms, 57 of 234 ms, 22 of 142 ms for the jobs in order. See CPU for functions.

Evidence and limits

  • Paired campaigns: runs 42808611154 (4 workers) and 42808599890 (2 workers); scored, ratios re-derived from raw rows.
  • Controller job timeline: run 42809383591 at 805e6a0 (one overhead-bearing run at 4 workers; passed: True). The first mutant batch also carries the diagnostic's CPU-profile window.
  • Node CPU profiles: run 42809377478 at 1b24aba, main with the #43 profiler tooling; passed: False, 17 of 18 fork profiles present (partial evidence; the capture's strict gate fails).
  • All four runs declare the same workload (b6a51df85b96).
  • The two scored campaigns (and the Stryker medians in them) ran on different runner hosts; compare ratios, not absolute times, across them.
  • Diagnostic runs land on different runner hosts and carry clock or profiler overhead. Durations are comparable only inside one capture.
  • CPU profiles sample each process's main thread only; Stryker leaves no profile.
