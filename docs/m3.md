# M3: conservative test selection

M3 adds baseline hit collection and test selection, on by default (as StrykerJS's
`coverageAnalysis: perTest` is):

```sh
cargo build -p oximut-cli --locked
target/debug/oximut --root fixtures/m3 --source src/subject.ts \
  --report .oximut/m3.json
```

Selection works with `--execution fresh` and with the default persistent execution.
`--no-test-selection` opts out and runs the full suite for every mutant, the
correctness reference. `--test-selection` is accepted and means the default; combining
it with `--no-test-selection` is an error. Both modes retain fresh test forks and
activate mutations before module evaluation.

## Attribution and selection

An original full-suite baseline validates the project. A separate unmutated,
probe-instrumented run records mutant hits and stable test identities. Instrumentation
must preserve the original expressions' values and evaluation order.

Selection retains every test in a file that hits a mutant. Keeping the entire
file preserves sequential dependencies: a first test can change module state
through a mutated function, while a later test detects the change without calling
that function itself. Stable per-test hit identities remain available in the
report even though this milestone selects at file granularity.

Import-time execution, suite initialization, concurrency, and uncertain attribution
require broader execution. Hooks must never be treated as evidence that only one
test matters. Global setup and unsupported configurations also require conservative
fallbacks. Reports explain fallback decisions rather than silently claiming precise
attribution. Per-test hooks retain their entire test file; suite hooks and suite
initialization execute the full suite. Inspecting a probe-instrumented function
through `Function.prototype.toString` also triggers full-suite fallback: reflection
can detect a mutation without executing its expression.

No-coverage is assigned only after complete, sound collection establishes that no
test or broader execution context hit the mutant. Incomplete or unsupported
collection cannot establish no-coverage. A requested source that was not observed
passing through the transform pipeline triggers full-suite fallback, including a
wholly unimported module. Uncalled functions inside observed modules can still be
classified as no-coverage. The existing score denominator includes
no-coverage alongside killed and survived mutants.

## Files that cannot carry probes

A probe is a free reference to `globalThis` calling the reserved
`__oximut_m3_hit__` hook. Merely reading the global (`typeof globalThis`,
`globalThis.Buffer`, `globalThis.x = 1`) cannot change what that reference
resolves to, so such files are probed normally. A file is refused only when the
reference could resolve to something else (a binding named `globalThis`, a `with`
scope, or an assignment to `globalThis` itself) or when it names the reserved
hook. That is a per-file decision: the refused file's mutants run the full suite
with the selection reason `unprobed-file: <file>: <reason>` (and a diagnostic
names the file), and its mutants are left out of the inventory the baseline must
attribute. Every other file keeps precise selection. Run-level fallback
(`incomplete-attribution`) is reserved for genuinely unsound run-wide
attribution (see below).

## Setup files

`setupFiles` do not disable selection. Oximut installs its probe hook ahead of the
user's setup files, and a hit is attributed to the test Vitest is running at that
moment:

- A setup file runs before each test file, outside any test. Code it executes while
  loading (importing a mutated module, top-level calls) has no test to blame, so those
  hits are recorded as outside-test execution. Exactly those mutants run the full
  suite with the reason `outside-test-execution`, as for any module-load mutant.
- A `beforeEach`/`afterEach` a setup file registers runs inside each test's lifecycle, so
  its hits belong to the test it wraps (if Vitest runs one while no test is current, the
  hit is outside-test and the mutant runs the full suite). Hooks never narrow past the file (the whole
  test file is kept), and a mutant a hook reaches in every test selects every file.
  `beforeAll` and suite bodies never have a current test and are always outside-test.
- Mutants that only tests reach keep their narrow selection, with or without setup files.

The run-wide `incomplete-attribution` fallback remains for cases where hits cannot be
tied to a test or to a safe context, each with its own reason:

- `global-setup`: a Vitest `globalSetup` runs once in the host process, outside every
  probe and test window, and can seed state (files, ports, environment) every test file
  then depends on.
- `concurrent-tests`, `retried-or-repeated-tests`, `shuffled-tests`: one hit stream
  cannot separate overlapping or repeated tests.
- Unsupported contexts: multiple projects, a non-node environment, externalized
  dependencies, a custom runner or custom Vite plugins, where hits or transforms may
  escape the observed pipeline.
- `source-reflection`, `source-not-transformed`, `probe-record-limit` and invalid or
  missing probe records: observation itself was incomplete.

## Coverage at scale

Baseline coverage lists every test and, for every mutant, the tests that hit it. A response
may be at most 1 MiB, and the inventory alone is a few hundred bytes a test, so coverage for
a suite of thousands of tests cannot travel in one. Every stage of the reference adapter is
sized for a suite far larger than that, so a big suite keeps its narrow selection instead of
running the whole suite for every mutant:

1. **The probe is O(1) and allocation-free.** `__oximut_m3_hit__` looks the mutant up in a
   `Map`, compares the last test that hit it with the running one, and returns. Only the
   first hit of a (mutant, test) pair is recorded, as a small integer into a per-process
   table of mutant ids, batched and written before the current turn of the event loop ends
   (so records survive fresh-fork termination). A hot parser loop costs a lookup and a
   comparison per hit instead of a `JSON.stringify` and a set lookup (about 30 times
   less). The bookkeeping is in `probe-recorder.ts`; the stream format is documented there.
2. **Aggregation is dense.** The controller reads the streams into one bitset per mutant over
   the sorted test inventory and emits each hit list as `testRanges`, inclusive `[first, last]`
   index runs (tests of one file are contiguous in that order, so a mutant every test reaches
   costs one run). Few hits (20,000 pairs or fewer in all) stay explicit `tests`, as before.
3. **Coverage travels by file when the CLI offers one.** The CLI creates a private directory
   for the coverage run (mode 0700, removed afterwards) and passes it as the request's
   `coverageDir`. The reference adapter writes the whole coverage payload there, with no
   response limit, as `coverage-<pid>-<n>.json` (created exclusively, owner-only), and the
   response carries only `coverageFile`, the plain file name. The CLI is the validator: the
   name must be a plain file name (no directory part, not hidden), the file must be a regular
   file, not a symbolic link, owned by the directory's owner and writable by nobody else, and
   at most 512 MiB; then it parses it strictly (unknown fields are refused) and runs the same
   inventory checks and `testRanges` checks as for an inline payload. Anything invalid
   (`invalid-coverage-file: ...`, `invalid-coverage-ranges`, `invalid-coverage-inventory`)
   makes coverage incomplete, so every mutant runs the whole suite, as for any incomplete
   coverage. Selection is an optimization; it never fails a run.
4. **Selection reads the runs.** The CLI keeps hit lists as index runs while it selects, so no
   per-mutant list of test ids is built (that would be mutants times tests strings).
   The report lists explicit test ids as before, unless they would exceed 250,000 in all;
   then hits keep `testRanges` (see [report-schema.md](report-schema.md)).

Other adapters keep the inline form: coverage that fits one response is sent as collected;
otherwise hits may use `testRanges` as above; coverage that still does not fit is dropped with
the reason `coverage-payload-too-large` and every mutant runs the whole suite. An adapter may
ignore `coverageDir`, and the reference adapter falls back to the inline form when it cannot
write the file.

## Reports and validation

Each mutant's `selection` records its mode, selected and total test counts, and
reasons, with `files`, `full`, and `none` modes. Text reports include the selected
count and fallback reasons too. The collected baseline coverage records test identities, mutant hits,
completeness, and diagnostic reasons. Invalid or missing coverage inventories
fall back conservatively; failed probe baselines block mutant execution. Selected
passing runs must match the expected test counts before becoming survivor evidence.

The selection acceptance corpus compares outcomes with the full-suite reference,
including shared state, hooks, duplicate test names, imports, concurrent tests,
and global setup. An uncovered mutant may change from survived in the full-suite
reference to no-coverage in selection mode; a killed mutant must never lose its kill.

```sh
python3 -m unittest discover -s tests -p 'test_m3*.py' -v
node --test packages/vitest-adapter/test/m3.test.mjs
```

The M3 gate passed on this corpus in fresh and persistent modes, with no missed
kills versus the full-suite reference. Adapter regressions additionally cover
source reflection, native loading, incomplete selection inventories, and clearing
probe state and filters between persistent jobs.

This is a correctness milestone, not a measured performance claim. Compatibility
remains limited to the pinned Linux/Node/Vitest combination. Selection assumes
files are independent outside their fresh JavaScript module state. Tests that communicate through files, databases, services, or other external
state must use full-suite execution; fresh forks do not isolate those effects.
Code executed outside the observed Vitest transform graph, such as native loading,
custom VM contexts, or user-created workers, is outside the proven attribution
boundary. Unobserved requested sources trigger fallback; projects mixing those
contexts with transformed copies should use full-suite execution.
Within-file test pruning, caching, and resource budgeting remain outside M3.
