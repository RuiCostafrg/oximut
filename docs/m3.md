# M3: conservative test selection

M3 adds opt-in baseline hit collection and test selection:

```sh
cargo build -p oximut-cli --locked
target/debug/oximut --root fixtures/m3 --source src/subject.ts \
  --test-selection --report .oximut/m3.json
```

`--test-selection` works with fresh execution and with `--execution persistent`.
Without it, execution remains the full-suite correctness reference. Both modes
retain fresh test forks and activate mutations before module evaluation.

## Attribution and selection

An original full-suite baseline validates the project. A separate unmutated,
probe-instrumented run records mutant hits and stable test identities. Instrumentation
must preserve the original expressions' values and evaluation order.

Selection retains every test in a file that hits a mutant. Keeping the entire
file preserves sequential dependencies: a first test can change module state
through a mutated function, while a later test detects the change without calling
that function itself. Stable per-test hit identities remain available in the
report even though this milestone selects at file granularity.

Import-time execution, suite initialization, concurrency, and uncertain attribution
require broader execution. Hooks must never be treated as evidence that only one
test matters. Global setup and unsupported configurations also require conservative
fallbacks. Reports explain fallback decisions rather than silently claiming precise
attribution. Per-test hooks retain their entire test file; suite hooks and suite
initialization execute the full suite. Inspecting a probe-instrumented function
through `Function.prototype.toString` also triggers full-suite fallback: reflection
can detect a mutation without executing its expression.

No-coverage is assigned only after complete, sound collection establishes that no
test or broader execution context hit the mutant. Incomplete or unsupported
collection cannot establish no-coverage. A requested source that was not observed
passing through the transform pipeline triggers full-suite fallback, including a
wholly unimported module. Uncalled functions inside observed modules can still be
classified as no-coverage. The existing score denominator includes
no-coverage alongside killed and survived mutants.

## Reports and validation

Each mutant's `selection` records its mode, selected and total test counts, and
reasons, with `files`, `full`, and `none` modes. Text reports include the selected
count and fallback reasons too. The collected baseline coverage records test identities, mutant hits,
completeness, and diagnostic reasons. Invalid or missing coverage inventories
fall back conservatively; failed probe baselines block mutant execution. Selected
passing runs must match the expected test counts before becoming survivor evidence.

The selection acceptance corpus compares outcomes with the full-suite reference,
including shared state, hooks, duplicate test names, imports, concurrent tests,
and global setup. An uncovered mutant may change from survived in the full-suite
reference to no-coverage in selection mode; a killed mutant must never lose its kill.

```sh
python3 -m unittest discover -s tests -p 'test_m3*.py' -v
node --test packages/vitest-adapter/test/m3.test.mjs
```

The M3 gate passed on this corpus in fresh and persistent modes, with no missed
kills versus the full-suite reference. Adapter regressions additionally cover
source reflection, native loading, incomplete selection inventories, and clearing
probe state and filters between persistent jobs.

This is a correctness milestone, not a measured performance claim. Compatibility
remains limited to the pinned Linux/Node/Vitest combination. Selection assumes
files are independent outside their fresh JavaScript module state. Tests that communicate through files, databases, services, or other external
state must use full-suite execution; fresh forks do not isolate those effects.
Code executed outside the observed Vitest transform graph, such as native loading,
custom VM contexts, or user-created workers, is outside the proven attribution
boundary. Unobserved requested sources trigger fallback; projects mixing those
contexts with transformed copies should use full-suite execution.
Within-file test pruning, caching, and resource budgeting remain outside M3.
