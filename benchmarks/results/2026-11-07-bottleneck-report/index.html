3. Ranked bottlenecks

#1 Fresh-process tax: 18 Node processes per run

1010 ms wall in bootstrap (33% of the run); forks consume 71% of Node CPU (partial: 17 of 18 fork profiles), yet only 7% of busy fork CPU is colord code and tests. The rest is Node bootstrap, module loading/compile, Vitest/expect/chai setup and GC, repeated in every process.

  • Build a V8 startup snapshot of the Vitest fork runtime (node --snapshot-blob), so each fresh process starts with the runtime already initialized. This keeps the fresh-process guarantee.
  • Opt-in warm runtime: strictly opt-in, per the owner's decision; default stays fresh forks.
  • Trim per-fork setup: only load what the selected test file needs (setup files, reporters, coverage hooks).

#2 Two full baselines before the first mutant

2.43 s of wall per run: controller start (~201 ms in the capture) plus 8 forks that each run one test file.

  • Run both baselines in one Vitest run (8 specs in one call) to share pool and controller warm-up.
  • Start the instrumented baseline while the original one is still running (overlap, same total CPU).
  • Keep the original baseline as the oracle, and question whether every file needs both runs.

#3 Killed mutants likely pay for failure formatting

444 ms of test time across 10 mutant jobs, versus a median of 18 ms per passing baseline file.

  • Bail on the first failure (Stryker uses bail: 1): the mutant is already killed.
  • Skip diff and stack formatting in mutant jobs (chai truncateThreshold, diff off).

#4 Oximut's own memory sampler

0.73 s CPU per run (10% of Oximut's CPU in that capture), 98 samples on the scheduler thread, almost all kernel time in smaps_rollup page walks.

  • Sample less often when nothing can be admitted (one worker, no memory pressure).
  • Drop periodic samples on the dispatch path; keep forced samples at admission/response.
  • Read cgroup memory.current when Oximut owns a cgroup (one cheap read per sample).

#5 Controller transform work on the critical path

The controller spends its busy time on Vite transforms, inline source-map scanning (regex over module text) and spawning forks, while the fork waits in its fetch/collect step.

  • Pre-transform resident modules once and serve cached results (already partly done by instrument-once).
  • Disable source maps for mutant jobs where no coverage or stack mapping is needed.

The ideas listed are discussion candidates, not measured savings. Each would be its own PR with a paired native benchmark and the owner's rule: faster with no added CPU or memory.
