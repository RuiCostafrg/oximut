# M5 — CPU and memory budgets

The Linux runner owns mutation concurrency in one central Rust event loop. It
accepts `--workers N` (positive integer, default 1),
`--memory-budget-mib N`, and `--memory-reserve-mib N` (default 64).
One MiB is exactly 1,048,576 bytes. The budget defaults to host `MemTotal`,
clamped to every visible finite ancestor cgroup memory limit. An explicit budget
is also clamped to those limits. Reserve must be smaller than an explicitly
configured budget. An effective limit smaller than reserve cannot admit work
and produces a resource failure rather than waiting indefinitely.

```sh
cargo run -p oximut-cli -- --root fixtures/m1 --source src/subject.ts \
  --execution persistent --test-selection --workers 2 \
  --memory-budget-mib 1024 --memory-reserve-mib 64 --report .oximut/m5.json
```

Requested workers are bounded by CPU affinity/available parallelism and visible
ancestor cgroup v1 CPU quotas or v2 `cpu.max`. Fractional quotas permit at least
one worker; this is a concurrency bound, not a CPU-time allocation. Vitest uses
one isolated fork, sequential files, and `maxConcurrency: 1` inside each slot.
Final resolved pool, isolation, worker, concurrency, and single-project settings
are checked; unsupported project configurations fail explicitly. The adapter's
libuv and Rust/Rayon helper pools are limited to one thread. User test code,
plugins, native libraries, and subprocesses can still create their own threads.

Each slot is a dedicated Rust subreaper subprocess. It owns its adapter,
Python cleanup supervisor, Vitest controller, and fresh test forks. Persistent
mode retains the safe controller reuse boundary established in M2; each mutant
still receives fresh test-process/module evaluation. Slot ownership prevents
one timed-out job from collecting or killing a parallel sibling's processes.
An unexpected slot-root death aborts admission, cancels all active work, and
triggers a final sweep of adopted descendants after all slot roots stop.
SIGINT/SIGTERM also cancel admission and clean up owned descendants. SIGKILL of
the main runner cannot execute cleanup.

The main controller samples Linux `/proc/PID/smaps_rollup` `Rss` for itself and all
transitive descendants every 50 ms, and forces another sample before accepting
each result. On older or restricted kernels where rollups are unavailable, it
falls back to approximate `/proc/PID/stat` RSS. The measurement description in
the report identifies this preference and fallback. Rollups avoid the stale
resident-page counters observed during short calibration runs on the recorded
host. Invalid accounting fails closed; a confirmed exited process has no live
working set. PID/start-time identities guard cleanup against PID reuse.
Adapter, controller, supervisor, Rust slot, and test-process memory are included.
Shared resident pages are counted once per process, so this is a conservative
RSS sum rather than unique physical memory. The two aggregate/per-slot scans
are reconciled conservatively so slot observations can never receive credit
against admission reservations absent from aggregate accounting. Short-lived
processes and allocations between samples can be missed. Accounting errors stop
admission with an explicit incomplete result; disappearing processes are normal.

A serial baseline calibrates observed peak slot cost before mutation jobs are
admitted. Admission reserves the maximum measured slot cost plus 25%, reserved
headroom, current aggregate RSS, and outstanding growth reservations for every
active job. It also checks host `MemAvailable` and each visible ancestor cgroup's
remaining memory. Memory and CPU cgroup paths are resolved from the process's
membership and mount roots, including ancestors exposed by those mounts.
Both initially unlimited and finite memory limits are tracked as they change.
Where available, v2 `memory.events` OOM-kill counters or v1 `memory.failcnt`
increases stop the run conservatively; shared-group events may originate from
another workload.

When admission lacks headroom, new work pauses and idle slots/controllers are
recycled. Active jobs may finish. Once no active jobs remain, failure to admit
one job after a bounded 250 ms pressure pause stops admission explicitly.
An observed aggregate overrun cancels active process trees and marks all
in-flight and pending jobs `resource-exhausted`. No such job is retried.
Resource failure wins over a ready failed-test response, never counts as a
mutation kill, is excluded from the score denominator, makes the report
incomplete, and exits with code 2. Baseline exhaustion blocks mutant execution.
Unexplained crashes remain infrastructure errors. Budgeted adapter invocations
disable the older crash-retry path so OOM-like crashes cannot loop.

The `resources` JSON object records configured/effective workers, CPU bounds,
configured/effective budget and reserve in bytes, visible cgroup paths/limits,
measured/admission slot cost, peak aggregate RSS, sampling interval, sample
count, peak active jobs, pauses, recycling, exhaustion reason, and enforcement
semantics. `summary.resourceExhausted` is separate from infrastructure failures.
Worker/resource policy, effective memory budget, normalized ancestor limits,
and effective CPU bounds participate in M4 execution fingerprints. Dynamic
usage and measured peaks do not. Warm results still require fresh baseline
validation; resource failures cannot publish reusable outcome bundles.

This is **best-effort admission and sampled cancellation**, not an installed
hard memory cap. It can overshoot before the next sample, and baseline cost
cannot predict arbitrarily more expensive mutants. Existing cgroup limits are
OS-enforced and apply to their whole group, possibly including other workloads;
this runner does not create or modify cgroups. RSS and cgroup charged memory
have different accounting rules. No byte-perfect compliance, CPU-time cap,
portable enforcement, or parallel speedup is claimed.

Acceptance coverage is in `tests/test_m5.py`: serial/parallel equivalence in
fresh and persistent modes, bounded overlap and measured admission under
steady pressure, idle recycling, detached descendant memory exhaustion with
one attempt and no cache publication, tiny-budget baseline rejection, timeout
cleanup preserving siblings, unexpected slot-root death, and SIGTERM cleanup.
Rust tests cover namespaced/ancestor cgroup resolution, unlimited/finite memory
limits, OOM counters, and execution-fingerprint invalidation when effective
container memory changes. Existing M1–M4 suites and real multiworker
selection/cache comparisons remain part of the release gate.
